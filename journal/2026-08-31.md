# Journal 2026-08-31

## 2026-08-31 — Entry syntax is plain markdown with named fields, not frontmatter

Baseline: 2116462

Decision:
- An entry is a `##` heading beginning with an ISO date, followed by
  `Baseline:` / `Decision:` / `Facts:` / `Assumptions:` / `Next:` / `Corrects:`
  fields. No YAML frontmatter per entry, no HTML comments carrying metadata.

Facts:
- The rule the whole format exists to enforce is that facts and assumptions stay
  apart, and named field headings put that split on screen where a reader sees
  it without tooling (src: docs/FORMAT.md)
- Fenced code blocks are made inert by the parser, so a pasted terminal
  transcript inside a fact cannot be misread as structure
  (src: lib/parse.js)

Assumptions:
- Assistants write markdown headings and bullets more reliably than they write
  well-formed YAML inside a markdown file. This is a judgement about model
  behaviour, not something measured here.

Next:
- Revisit if real use shows entries needing fields that prose cannot carry.

## 2026-08-31 — Append-only is enforced by byte-prefix comparison against HEAD

Baseline: 2116462

Decision:
- R5 compares each journal file with `git show HEAD:<path>` and requires the
  committed bytes to be a prefix of the working copy.

Facts:
- A byte-prefix test catches every edit to committed text, including deletions
  and reordering, without the checker having to understand entry boundaries
  (src: lib/rules.js)
- The check reports the line where the two versions first diverge, computed by
  counting newlines in the common prefix (src: lib/rules.js)
- A journal file absent from HEAD is treated as new and passes, so a first
  commit is not blocked (src: $ node --test)

Assumptions:
- Nobody needs to reflow or reformat old journal prose. If that turns out to be
  wrong, the rule has no escape hatch short of `--no-verify`.

## 2026-08-31 — A delivery with no entry now fails, and R5 gets its one written exception

Baseline: 61e6f51

Decision:
- `logbook check --require-entry-since <git-ref>` fails when the journal has
  gained no complete entry since that revision. It is an option rather than a
  sixth rule: the five rules run everywhere and need no argument, while this one
  cannot run until a caller says what the delivery is.
- An entry counts as complete when it has a `Baseline:` that is a hash rather
  than the template placeholder and at least one item under `Decision:` or
  `Facts:` that is more than placeholder text. Running `logbook add` therefore
  does not satisfy the gate; only filling the skeleton in does.
- A revision that does not resolve is an error, not a pass. The first-push case,
  where there is genuinely nothing to compare against, is handled in
  `hooks/pre-push` instead, because git hands that hook the remote's commit id
  on stdin and a run of the option does not know it. Putting the exemption in
  the checker would also let a misspelled branch name switch the gate off in
  silence, which is the failure the gate exists to prevent.
- `docs/FORMAT.md` now defines the single case where committed journal text may
  be touched: a git history rewrite, remapping only `Baseline:` hashes, inside
  the same rewrite, each new id naming the same underlying commit. The entry
  below at line 132 did exactly this and the specification did not cover it.
- `LOGBOOK.md` gains a `Status:` line, one sentence rewritten whenever the
  project moves. It sits there and not in a journal entry because `LOGBOOK.md`
  is the layer that may be overwritten and `journal/` is the layer R5 freezes.

Facts:
- A logbook with no entries passes every rule: `logbook init` followed by
  `logbook check` in a fresh repository reports "logbook check passed: 0 entries
  in 0 journal files" and exits 0 (src: $ node bin/logbook.js init; node bin/logbook.js check)
- The suite is 49 tests, all passing, up from the 34 that existed before this
  work (src: $ node --test)
- git passes the pre-push hook one line per ref as
  "local ref, local sha, remote ref, remote sha", and the remote sha is all
  zeros when the remote has no such branch, which is what lets the hook
  recognise a first push without a network call
  (src: https://git-scm.com/docs/githooks#_pre_push)
- The `skills/logbook/SKILL.md` rule that told a writer to skip a rename
  contradicted this repository's own densest entry, the rename at line 72, which
  carries five checked facts (src: journal/2026-08-31.md)
- The authorship rewrite entry at line 132 is where the baseline-remap exception
  was first recorded, as a fact about one incident rather than as a rule
  (src: journal/2026-08-31.md)

Assumptions:
- The gate will be tolerable in daily use rather than something people learn to
  push past with --no-verify. Nothing here measures that; it is the reason the
  failure text names writing the entry as the fix and calls an invented entry
  worse than none.
- The pull-request step added to the CI workflow resolves `origin/<base branch>`
  under `actions/checkout` with `fetch-depth: 0`. This was reasoned from the
  checkout action's behaviour, not observed on a real pull request, because this
  repository has had none.

Next:
- Watch the first real pull request to confirm the CI step resolves its base
  branch, and correct this entry if it does not.
